# Orchestra 架构文档

> 文档编号：T5
> 日期：2026-11-14
> 对象：CLI 多 agent 调度器 Orchestra
> 自检：node --version && wc -l docs/ARCHITECTURE.md（应为 180-260 行）

本文描述 Orchestra 的静态分层与一次调用的动态流转。全部事实取自当前
代码库，不引入未落地模块，也不把失败的派活记为既存能力。

## 一、定位与设计原则

Orchestra 是纯命令行形态的多 agent 调度器。它自身不做模型推理、不监听
端口、不提供 Web 界面、不引入任何框架；唯一职责是：接收一批任务，按各
执行端的能力边界挑选 agent，并发跑起来，再把异构输出收敛成统一 JSON
契约交还调用方。

技术栈为 Node.js 24 纯 ESM，只用 import/export，只用 node: 前缀的内置
模块，零第三方依赖。这不是审美偏好而是部署约束：调度器常被塞进一个刚
克隆完、还没跑 npm install 的仓库，任何安装步骤都会让首跑失败；零依赖
使 orchestra.mjs 可以直接被 node 起来。

代码统一 2 空格缩进、单引号、行尾分号。所有导出函数写中文 JSDoc，且
必须解释「为什么这么做」而不只复述「做了什么」——本项目大量依赖隐式
协议（锁的 stale 判定、prompt 分区预算、契约 5 级修复），只写 what 会让
后来者不敢改动边界条件。

由此得出三条原则：

1. 入口极薄。orchestra.mjs 约 800 行，靠 if (cmd === ...) 逐条分派，
   不抽象成命令注册器，好让任一命令的执行路径都能在一屏内读完。
2. 差异下沉。三个 agent 的驱动方式完全不同（CDP / spawn），这些差异
   必须被 agents/ 吃掉，编排层只看得到同一个调用签名。
3. 一切收敛为数据。锁、预算、契约、缓存都以纯数据流转，便于 CLI 无
   守护进程的前提下做断点续跑。

## 二、分层视图

分四层，箭头为调用方向，同层从左到右为流水顺序。

    +------------------------------------------------------------+
    | L4 调用方：终端 / 上层脚本                                  |
    |   node orchestra.mjs <cmd> --agent ... --task ...           |
    +-------------------------+----------------------------------+
                              | argv / stdin
                              v
    +------------------------------------------------------------+
    | L3 入口层：orchestra.mjs（约 800 行，if cmd === 分派）      |
    |   纯 CLI 无框架：解析 -> 选模块 -> 汇总 -> 写退出码          |
    +-------------------------+----------------------------------+
                              v
    +------------------------------------------------------------+
    | L2 编排层：lib/                                            |
    |   preflight -> prompt -> budget -> cache -> batch -> swarm  |
    |        -> contract -> syntax -> store -> project-memory    |
    |   lock 横切全程：互斥与 stale 抢占                          |
    +-------------------------+----------------------------------+
                              v
    +------------------------------------------------------------+
    | L1 适配层：agents/                                         |
    |   trae.mjs(880)  codebuddy.mjs(158)  workbuddy.mjs(232)     |
    |     CDP             spawn CLI            CDP                  |
    +-------------------------+----------------------------------+
                              v
    +------------------------------------------------------------+
    | L0 执行端                                                   |
    |   Trae 桌面应用    codebuddy 子进程    WorkBuddy 桌面应用     |
    +------------------------------------------------------------+

分层的关键是 L2 与 L1 之间只有一条窄接口：编排层传入组装好的 prompt 与
任务描述，拿回一段文本；至于文本是 CDP 里点出来的还是子进程 stdout 读出来
的，编排层不关心。反过来 L1 也不许直接读写 store 或 cache，否则并发一致
性会散落到三个适配文件里，无法统一。

lock 是唯一横切模块：它不在流水线上，而是包住整条流水线，防止两个进程
同时改同一份 project-memory 与 store。

## 三、一次调用的生命周期

按真实执行顺序编号。一次调用指一个 cmd 从进入到写出结果的全过程。

1. 入口分派。orchestra.mjs 读 process.argv，用 if (cmd === 'run') 之类
   的分支选中命令，把余下参数归一为 options 对象。没有路由表、没有
   中间件，分支本身就是控制流。
2. 抢锁。lib/lock.mjs 以 O_EXCL 创建锁文件，成功者持有；失败者读锁内
   心跳时间戳，判定 stale 后才抢占。用 O_EXCL 而非先判存再创建，是为了
   让一个原子动作同时完成「判存」与「占有」，避开 check-then-act 竞态。
3. 预检。lib/preflight.mjs 检查执行端是否就绪：桌面应用开没开、CDP 端口
   能不能连、CLI 在不在 PATH。把失败挡在派活之前，省掉一轮 54-118 秒的
   无效等待。
4. 组装 prompt。lib/prompt.mjs 按六分区拼装并逐区裁剪，字符预算固定：
   task 20000、memory 1200、project 900、ephemeral 1200、skill 3000、
   contract 1400。写死而非按比例动态分配，是因为 codebuddy 的输入 token
   固定 7633，超了会被静默截断。
5. 预算核算。lib/budget.mjs 按任务数与各 agent 历史耗时估算时间和 token，
   超阈值的任务拆到下一批或直接拒绝。
6. 查缓存。lib/cache.mjs 以任务内容加 prompt 版本算键，命中则跳过 7-11
   步直接返回。键必须带 prompt 版本，否则六分区策略一改，旧结果会以新
   口径被复用。
7. 合批。lib/batch.mjs 把 N 个同 agent 的任务压进一次调用。动机是
   codebuddy 单次要 54-118 秒，逐任务调用会把固定开销乘以 N；压成一次
   后 N 个任务共享这一轮启动成本。
8. 分组并行。lib/swarm.mjs 按 agent 分组并发。分组而非全局混跑，是因为
   并发上限不同：trae 1 路、codebuddy 6 路、workbuddy 受单实例限制。
   组内组间都并发，但每组各自持有信号量，互不挤占。
9. 适配执行。agents/ 下对应文件接管：trae.mjs 与 workbuddy.mjs 走 CDP
   驱动桌面应用，codebuddy.mjs 直接 spawn 子进程读 stdout；三者统一把
   结果吐成纯文本上交。
10. 契约修复。lib/contract.mjs 要求合法 JSON，不合要求时按 5 级修复逐级
    升级：清洗包裹文本、补缺字段、纠正类型偏差、按 schema 重建、最终
    降级为带错误标记的兜底对象。分级而非一次强转，是为了尽量保住模型
    已经写对的那部分。
11. 语法校验。lib/syntax.mjs 对返回体里判定为代码的部分做 node --check
    级别的检查，挡住肉眼就能看出跑不起来的产物，且只校验不执行。
12. 落盘与记忆。lib/store.mjs 写结果，lib/project-memory.mjs 沉淀可复用
    的项目事实供下一次第 4 步的 project 分区使用；最后释放锁并终止心跳。

第 2 步与第 12 步必须成对，释放锁要落在 finally 语义里：CLI 被 Ctrl+C
打断时不走正常收尾，锁只能靠下一轮的 stale 抢占回收。

## 四、模块逐段说明

按 L3 -> L1 -> L2 顺序，每段对应一个文件。

### 4.1 orchestra.mjs（入口，约 800 行）

唯一「必须存在」的文件。用 if (cmd === ...) 把 run、批量、查询、清理等
子命令逐条分派，纯 CLI、无框架、无依赖注入。800 行里大部分是参数归一化
与错误文案，真正的编排逻辑都下沉到 lib/。不做命令注册器，是因为命令数
长期稳定在个位数，抽象带来的间接跳转比多写几个分支更贵。

### 4.2 agents/trae.mjs（880 行，CDP 驱动 Trae 桌面应用）

最厚的一个：CDP 会话管理、DOM 查询、输入注入、回合等待几乎全要手写。
能力画像是单次 19-36 秒、只有 1 路并发、散文强而代码弱，且第 12 回合
之后会触发 DOM 虚拟化——早先靠选择器能拿到的节点会突然从可查询树消失。
因此文件内对长会话做了回合切分，不把超过 12 回合的上下文压进一次会话。
它适合写文档与说明，不适合承接代码任务。

### 4.3 agents/codebuddy.mjs（158 行，spawn CLI）

最薄的一个：spawn 子进程、喂 stdin、收 stdout，几乎不需要状态机。能力
画像是 54-118 秒、可到 6 路并发、代码强，且输入 token 固定 7633。这个
固定值解释了为何 prompt.mjs 要把六分区预算写死——适配层没能力替上游做
动态裁剪。慢但可并发，所以 batch 与 swarm 的优化主要针对它。

### 4.4 agents/workbuddy.mjs（232 行，CDP）

同样 CDP 驱动桌面应用，但比 trae.mjs 薄，因为不必处理长会话与 DOM 虚拟
化。单次 18-20 秒，三者中最快；硬前提是应用必须开着，桌面应用没启动即
整个 agent 不可用，所以 preflight 对它格外关键。

### 4.5 lib/lock.mjs

以 O_EXCL 创建锁文件实现互斥，锁内写持有者心跳；读锁方发现心跳超时即
判定 stale 并抢占。用文件锁而非内存锁，是因为 CLI 每次都是独立进程，没有
共享内存；用心跳而非纯存在性判断，是因为进程可能硬崩，只留一个空锁文件
会让后续所有调用永久堵塞。

### 4.6 lib/swarm.mjs

按 agent 分组并行，每组一套并发上限。分组的直接原因是三者能力不对等：
trae 1 路、codebuddy 6 路、workbuddy 受单实例限制。若全局一个池子，
codebuddy 的 6 路会把 CDP 侧唯一那 1 路也排队挤住。

### 4.7 lib/batch.mjs

把 N 个任务压成一次调用，且只压「同一 agent、同一 prompt 版本」的任务，
因为只有同批才能共享一次启动成本。批大小受 budget 约束，不能为了让
单次更划算而无限增大，否则一次失败会连带丢掉整批结果。

### 4.8 lib/contract.mjs

输出必须是 JSON 契约；不满足时走 5 级修复，从最轻的文本清洗逐级升到
按 schema 重建与带错误标记的兜底。分级是为了「尽量少改」：模型输出里
往往只有一层多余包裹，一刀切强转会丢掉正确字段。

### 4.9 lib/prompt.mjs

六分区固定预算：task 20000、memory 1200、project 900、ephemeral 1200、
skill 3000、contract 1400。分区隔离的意义在于「可预期地丢」：上下文
超长时，先裁 ephemeral 再裁 skill，绝不裁 task 与 contract，保证任务
主体和返回格式永远完整。

### 4.10 lib/budget.mjs

按任务数与各 agent 的历史耗时（19-36 / 54-118 / 18-20 秒）估算时间与
token，决定本轮放行多少、哪些留给下一批。它把能力差异变成可计算的数字，
让 batch 与 swarm 不必硬编码批大小。

### 4.11 lib/cache.mjs

以任务内容加 prompt 版本为键缓存结果，命中即跳过派活。键里必须带 prompt
版本：六分区预算一调整，旧缓存就属于旧口径，直接复用会静默产出错误结果。

### 4.12 lib/preflight.mjs

派活前检查执行端就绪：桌面应用是否开着、CDP 端口是否可连、CLI 是否在
PATH。对 workbuddy 尤其关键，它「需应用开着」是硬前提；把这类失败前置，
避免把 54-118 秒耗在一个根本连不上的目标上。

### 4.13 lib/syntax.mjs

对返回体中被判定为代码的部分做 node --check 级别的静态校验，拦下明显
跑不起来的产物。它只做语法层，不执行代码，避免调度器本身成为执行面。

### 4.14 lib/project-memory.mjs

沉淀跨调用复用的项目事实，供 prompt 的 project 分区（900 字符）读取。
预算只有 900，所以它必须做「提炼」而不是「堆日志」，否则最该被保留的
结论会被最早的行挤掉。

### 4.15 lib/store.mjs

结果落盘与历史读取，是 cache 与 contract 的共同下游。纯文件存储、无
数据库，延续零第三方依赖的约束；写入与锁的心跳共用同一份锁保护。

## 五、新增一个 agent 要改动哪些文件

新增 agent 的成本被刻意压在适配层，但并非只加一个文件：

1. agents/<name>.mjs：实现统一调用签名，把该执行端的驱动细节（CDP /
   spawn / 其它）全部封装在文件内，向上只返回纯文本。
2. orchestra.mjs：若新 agent 需要新的 cmd，则在 if (cmd === ...) 分派
   链里加一条分支；已有 cmd 只需扩展 --agent 的取值校验。
3. lib/swarm.mjs：登记该 agent 的并发上限，否则默认会被当成 1 路，
   或反过来挤占别组的额度。
4. lib/budget.mjs 与 lib/preflight.mjs：补耗时画像与就绪检查条件；
   前者决定批大小，后者决定能不能开工。
5. lib/prompt.mjs：若该 agent 的上下文窗口与现有六分区预算冲突，需要
   新增一份分区配置，而不是改动公共预算。
6. docs/ARCHITECTURE.md：把能力边界（耗时、并发路数、强弱项、硬前提）
   补进本文第二节与第 4 节，本文是这些数字的唯一文字出处。

不需要改动 contract、syntax、store、project-memory、cache、lock：它们
只看编排层的统一数据结构，与具体执行端无关。这正是分层的收益。

## 六、已知限制与风险

1. CDP 系执行端依赖 GUI。trae 与 workbuddy 都要桌面应用开着，无头环境
   不可用；preflight 只能提前报错，不能替你把应用拉起来。
2. trae 的 12 回合 DOM 虚拟化。长会话中途节点会从可查询树消失，适配层
   靠回合切分绕过，属于绕过而非根治，应用侧改版随时可能让切分策略失效。
3. codebuddy 输入 token 固定 7633。prompt 的六分区预算是为这个硬上限
   反推出来的，一旦上游调整 token 上限，六分区数字需要整体重算。
4. 单锁串行化。lock 把整条流水线包住，保证一致性，但也意味着同一工作区
   同时只能有一个 orchestra.mjs 在跑；多进程并行只能靠拆分工作区规避。
5. stale 抢占靠心跳超时。进程硬崩后要等一个心跳周期才被回收，期间新
   调用会等待；阈值调小则可能因一次长 GC 误判存活者为死亡。
6. 能力画像靠实测。19-36 / 54-118 / 18-20 秒与强弱项都是经验值，随
   agent 版本漂移；budget 的估算是基于这些值的推断，不是保证。
7. 合批放大失败半径。N 个任务压进一次调用，调用失败会同时影响 N 个任务，
   batch.mjs 的批大小因此必须留有余量。
