# 长尾切分：把「最慢那一个」本身变小（2026-11-16，rank2 / dsh-work-replace）

## 一、为什么切分，而不是加路数

并行墙钟 = 最慢那一个任务，不是平均值。

- 实测：12 个互不相同的任务，并行 216.8s，串行 1416s（12 × 118s 均值）。6.5× 的来源是「其余 11 个藏到最慢那个背后」。
- 推论：最慢那个不变大小时，路数从 6 加到 12 也不减少墙钟 —— 只有让它本身变小才有用。
- 并发曲线：1 路 4.85s / 3 路 4.92s（2.96×）/ 6 路 7.18s（4.05×）/ 12 路 12.46s（4.67×，单路由 4.85s 涨到 11.05s）。拐点在 6–8 路。

## 二、切分规则（都是可复算的纯函数，lib/split.mjs）

| 规则 | 值 | 理由 |
|---|---|---|
| 只切可枚举单元 | 任务文本里的 glob + 真实存在的文件名 | 抠不出就返回空、绝不猜；切法必须可复算，否则分不清「切错了」还是「活本来这么大」 |
| 最少单元数 | 4 | 4 个单元切成 2 片只是把同一份活写了两遍开头 |
| 每片最少单元 | 2 | 子会话固定成本：spawn 5–10s + 注入 400–800 token |
| 片数上限 | min(maxChunks, floor(units/2)) | 默认 4，命令行可到 6 |
| 合订方式 | 机械拼装，不调 LLM | LLM 合订是幻觉入口且慢；机械拼装可复算，落 MERGED.md |
| 单元可见性 | 剔掉 .gitignore 命中的文件 | 见下节，不剔必然假 REVISE |

## 三、三处「假失败」（这一轮真正花时间的不是切分本身）

### 1. 派下去的文件，子会话看不见

`detectUnits` 用 fs 读盘得到 78 个 `lib/*.mjs`；子会话的 Glob / Grep 尊重 .gitignore，只看得见 52 个。
于是子会话说「这些文件不存在」，父审用 Read 又读到了 → 判 REVISE。**不是能力问题，是两边文件视图不一致。**

修法：`git check-ignore --stdin` 批量过滤；git 不可用时不过滤（宁可多派，也不要把清单清空）。

### 2. 父审丢票（这一轮最贵的 bug）

codebuddy 默认 `--max-turns 10`。一片送 3 份产物，父审要核对几十个引用行 → 断在 `Max turns (10) exceeded`。
CLI 把这句话当正常输出返回，`parseReview` 解析不出 JSON → 3 条 `unreviewed`。

事后查了半小时才定位，因为**原始输出没有落盘** —— 看到的现象是「父审没给票」，真实原因在三个可能里（漏答 / 解析失败 / 调用失败），没有证据只能猜。

修法二连：
- 父审回合预算按片内份数给：`min(60, 12 + 份数 × 8)`；子会话按片内单元数给：`min(60, 8 + 单元 × 3)`。
- 空片不再静默记成「没给票」，而是「父审这一片调用失败：<错误>」或「返回了空内容」。

实测：同一 6 片任务，子会话 178.7s → 26.1s（此前三片全部撞满回合、挣扎到 180s 超时）；6/6 PASS。

### 3. 可观测性

`REVIEW-RAW.md` 原样保存父审输出，`FANOUT.md` 记 `summary.error`。
教训：**可观测性缺口比 bug 更贵** —— bug 修一次，缺口让你每次都在猜。

## 四、切分到底值多少（实测，不是理论）

| 任务 | 单路 | 切分 | 倍数 |
|---|---|---|---|
| 4 个文件 | 30.6s（子 19.2 + 审 11.3） | 2 片 25.1s（子 11.0 + 审 14.0） | 1.22× |
| 8 个文件 | 53s（子 20.2 + 审 32.5） | 4 片 38s（子 15.5 + 审 22.6） | 1.39× |
| 53 个文件「一条命令能扫完」 | 67s（子 42.2 + 审 25.1） | 6 片 110s（子 26.1 + 审 84.4） | **0.6×（变慢）** |

结论（必须记进判据）：
1. 切分把最慢那一路缩短 43%（19.2 → 11.0），但父审是固定成本，摊薄后总收益只有 1.2–1.4×，**不是理论上的 3–4×**。
2. **「一条命令能扫完」的活不要切**：单路一条 `grep -r` 就拿到全部答案，切开等于让 6 片各自重复探索，父审还要读 6 份产物。
3. 值得切的画像：单元多（≥8）、每个单元都要**深读**（读全文、逐条核对）、单元之间**不重叠**。

## 六、已知不对称与没做的

- 切分只切文件单元。切「按函数切」「按测试用例切」「按 git 目录切」都没做 —— 没有可枚举的干净边界，做了就是猜。
- `--split` 与 `--lanes` 同时用时，切分后的片全部落在**同一个通道**（第一个 lane 的 ask），没有按通道重新分配。原因：跨通道质量不同，同一任务的片交给不同质量的通道，父审没法用同一把尺子比。
- 父审回合预算上调后，单片父审可以慢到 84s（6 片时）。这是「读得更细」的代价，不是退化；但意味着 **8 份以上产物不要只靠一个父审**。
