## 1. 判断

**存疑**。机制层面有真东西——三值把「没评成」保留成独立状态，这是二值验收给不了的；但当前实现有两处能在 CLI 上直接复现的误判，且它没接进任何闸门：`atwo.mjs:432-560` 的 judge 只是子命令，`check`（packages/accept）与 `done`（`atwo.mjs:703-762`）都不消费它。所以今天它是一件能跑、但没上岗的仪器。

## 2. 最强理由三条（落到机制）

1. **第三态不被压缩。** `vm/votes.mjs` 只在 value=+1 且方向确定时才给 ACCEPT/REVISE，其余一律 unreviewed：实测 `ACCEPT,ACCEPT,REVISE` 置信度 0.109 → unreviewed，而按多数票（2:1）会判 ACCEPT——把「没共识」洗成「通过」，正是二值系统的老毛病。
2. **判定过程可复算。** judge 把 0.45/0.22 写成 AST→字节码→真跑，再与现算比对，不一致直接归 0（`reason:'compiler-mismatch'`）；字节码是有限数字串，可哈希、maxSteps 有硬上限、可跨语言逐帧回放，闭包式的 JS 判定函数给不了这三样。
3. **口径单一。** 阈值只在 `vm/judge.mjs` 的 CUT 定义一次，`votes.mjs` 复用同一分档、不另立数；`atwo judge --z` 与 `--votes` 走的是同一套 strength/agreement/nValid，避免两处阈值各写一遍的漂移（这是 atwo 多通道验收最常见的缺陷形态）。

## 3. 一个可检验的反例

直接跑：`node atwo.mjs judge --votes ACCEPT,ACCEPT,ACCEPT --expect 5`

输出「结论 ACCEPT（都认了，可以过）· 置信度 0.457」。算式：strength = tanh(1) = 0.762，agreement = tanh(1/1e-9) = 1，nValid = 3/5 = 0.6，乘积 0.457 ≥ 0.45。而实际只有 5 个应评里的 3 个到票，2 人没评成——40% 缺口下正确结论是 unreviewed。根因是 nValid 只做线性折扣、0.45 又是绝对阈：0.45/0.762 ≈ 0.59，意味着全员一致时只要 59% 的人到场就能过线，缺 41% 证据照样「可判」。

同型缺陷还有一处，同样一条命令可验：`--z` 传 9 个 0.5（同一弱信号复制）得 0.462 → 可判；只传 1 个 0.5 得 0.051 → 别判。sd=0 被 agreement 当成「完全一致」（tanh(0.5/1e-9)=1），把「指标重复、彼此不独立」读成「证据互相印证」，复制一列就能把结论从别判顶到可判。

## 4. 落点建议

只留一处：**done 收工闸门**。理由三条：其一，check 是逐文件二值验收（packages/accept 每项只有过/不过），放那儿等于把三态重新压成二值；其二，diff 只归并分歧、不回答「能不能收工」；其三，judge 单列成子命令就没人消费——现状就是它。done 是「假通过」直接变成返工的位置，也是唯一本来就允许「没评成」合法存在的地方（`reviews/` 里 unreviewed 是正常状态）。具体接法：在 `atwo.mjs:735-762` 的交付物验收与回归闸门之后加一次 `judgeVotes`（票面取 reviews/ 里本轮评审，expected 取应评人数），value ≤ 0 直接拒绝收工并提示补评，第三态才真正起作用。前提是先把第 3 条那个 nValid 线性折扣修掉，否则闸门会替 3/5 到票的活放行。
